# 数据删除：复用现有能力，补生产生命周期

2026-09-18，待审方案，未实施生产删除或新 Migration。

## 已经具备的删除图

账号删除事务已有密码重认证、最终 Session 校验、必需 Audit、User 删除与未知提交确认，并终止本进程 AI 和 Incognito。当前最新工作树的外键覆盖：

- User → Session、Credential、Age、Consent decisions、Conversation/Message/AI Turn、知识引用、Mood、Quota。
- User → 日记本 → 日记正文/草稿、照片；照片存于 PostgreSQL，无外部对象存储要额外删除。
- User → 个人设置、头像、简介、日记 AI policy/grants；日记 turn 引用随 AI Turn 删除。
- RiskEvent 按独立期限保留，部分用户/聊天关联置空；ReviewQueue 随 RiskEvent 生命周期。
- Audit、全局 Staff 和 Knowledge 独立。Audit 可能仍含旧 actor/resource ID，不能宣称全部匿名化。

单页日记删除同时删除该日照片；删除日记或关闭日记参考不会自动抹去旧聊天中已有的信息。用户要删除普通聊天仍走聊天删除，注销则清理整个账号主图。

## 生产缺口及最小方案

[ADR-022](../../architecture/adr/ADR-022-account-deletion-and-data-lifecycle-boundaries.md) 明确："Production needs a separate durable/cross-instance decision." 当前 service 与 env 双层只允许 Development/Test；不得只去掉 guard。

推荐首发保留 **单 API 进程**，不新增 Redis/队列。生产扩展仅补以下内容：

1. 在现有 PostgreSQL 中保存最小待处理注销状态，使 terminal/unknown 不随进程退出消失。记录只含内部主体绑定、operation 身份、状态和必要时间，不含邮箱、密码、聊天或正文 hash。
2. 使用现有 User 锁、Session/密码校验、coordinator 和 cascade。终结状态持久化后阻止该主体新处理；重启先确认/恢复未完成注销，再接收相关业务。所有 dispatch 和内容写入均需遵守该状态。
3. 原事务提交结果未知时继续串行确认，禁止重新发起一份删除。新状态不提供匿名查账户存在性的接口，不把“无法再登录”当成已删除凭证。
4. 成功后按批准期限清理暂存身份关联。其保留目的、期限、访问权限及备份覆盖必须在新 ADR 写明；不能为了无限重放永久保存注销主体。
5. 准备一个用户可用的注销入口及无法登录时的权利请求渠道。沿用当前 API 语义；前端接入由用户的前端任务负责，不擅自重做界面。

以上需要窄幅 supersede ADR-022 的本地-only/内存-only 边界。没有保留政策时不先创建一张永久 receipt/tombstone 表。本次没有实施这项 Schema 变更。

## 正式保留表需要落地的内容

| 数据                           | 已有工程语义                          | 公开前需要确认                                         |
| ------------------------------ | ------------------------------------- | ------------------------------------------------------ |
| 普通聊天                       | 默认 90 天；主动保存的保留至删除/注销 | 是否采用该产品期限、告知及定时清理                     |
| 日记/草稿/图片、心情、头像设置 | 账号存续期，用户可删除，注销 cascade  | 采用该期限及明确删除入口                               |
| Consent evidence               | 跟随用户主图删除                      | 正式政策是否要求额外留存；不得私下改变                 |
| Risk/ReviewQueue               | 默认风险期限 180 天，独立清理         | 真实必要目的与期限，不能把默认值当法定期限             |
| Audit/安全日志                 | 独立期限，可能保留内部关联            | 各自目的、字段、访问范围与期限；不把三者混为一种日志   |
| 数据库备份                     | 尚无正式运维政策                      | 服务商、加密、最短可行窗口、到期销毁、恢复前注销处理   |
| 模型服务商已接收内容           | 本站无法直接证明已删除                | 合同里的保留、训练用途与删除渠道；准确告知可做到的范围 |

已有 Conversation/Risk/Audit purge CLI，正式期限确认后接一个防重叠定时任务即可。不另写新的清理框架。

## 备份采用有限的上线规则

生产恢复点可能包含后来已注销的数据。恢复必须离线进行；在恢复对外服务前根据可信的删除记录补齐恢复点之后的注销，再核对结果。该记录不能只与待恢复数据库一起回退，其访问、保存窗口与销毁需随主机备份方案确定。

这里要求可执行的最小恢复规则，不恢复已暂停的 NF-04 多轮演练。没有可靠的注销重放证据时，不把旧备份直接对外开放，也不能声称已解决生产恢复。

## 结束条件与必要验证

结束条件：真实政策确定、生产状态/重启恢复完成、删除入口可用、定时清理已配置、备份不复活账号的处置路径明确。仅验证新增的持久状态/重启未知结果、最新日记/图片账号级 cascade、终结后拒绝新处理，以及该 Migration 的必要升级检查；不重复已有全量场景。

依据：[个人信息保护法](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)第 47 条及[网络数据安全管理条例](https://www.cac.gov.cn/2024-09/30/c_1729384452307680.htm)第 23 条。不能把工程默认值包装为法定保存期限；本方案未完成法律审查。
